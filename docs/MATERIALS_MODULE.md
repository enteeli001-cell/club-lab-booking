# 材料领取、购买与首次登录资料完善

本模块在原有代码基础上开发，并修正了资料门禁、邮箱变更、并发事务、邮件脱敏和关联数据清理等问题。

本轮新增分张购买及领取：数量、库存、每队份数、每次限购和记录更正均支持小数、分数及带分数，沿用原有权限、照片、邮箱核验、结算和审计流程。

## 分数数量与金额规则

| 输入 | 精确数量 | 单价 2.35 元时的小计 |
| --- | --- | --- |
| `0.5` | `1/2` | 1.18 元 |
| `1.25` | `5/4` | 2.94 元 |
| `1/3` | `1/3` | 0.78 元 |
| `2/3` | `2/3` | 1.57 元 |
| `1 1/2` | `3/2` | 3.53 元 |

队长数量框使用文本输入，手机可以输入 `/` 和空格。填写的购买数量必须大于 0；空白或单独的 `0` 表示不选该项，整单至少选择一项。库存允许 0，记录更正允许以 0 删除该项；每队份数和限购必须大于 0。可接受分数斜线两侧的普通空格，带分数的整数与分数部分以空格分隔；如 `1又1/2` 应写为 `1 1/2`。

输入最长 64 字符，小数最多 9 位、分母最大 1,000,000,000；拒绝负数、零分母、科学计数法、NaN/Infinity、非 ASCII 数字、不完整数字及超出数量上限的输入。数量/库存上限仍为 1,000,000，每队份数、每次限购和记录更正上限仍为 100,000。分数会自动约分，如 `2/6` 保存并显示为 `1/3`。材料型号/规格仍可留空，单价始终按一个完整单位（例如 1 张）计。

后端采用 Python `Fraction`，数据库用约分后的字符串精确保存，例如 `1/3`、`7/2`、`0`；前端使用 BigInt 有理数解析、比较和算价，两端均不使用浮点数量做扣库。页面、邮件、审计、统计和 Excel 统一显示精确数量；Excel 中整数量为数值，非整数量为文本，避免 `1/3` 被改成近似数或日期。

价格计算先以精确数量乘服务端的整数单价（分），**每条明细使用四舍五入 ROUND_HALF_UP 到分，再累加订单总价**。结算及材料销售金额统计累加已舍入的明细金额，与订单一致，不重新按汇总数量舍入。例如单价 1 元、三次分别购买 `1/3`，每笔 0.33 元、合计 0.99 元；库存则严格为 `1 - 1/3 - 1/3 - 1/3 = 0`，不会剩下一点误差。

精确库存运算可能生成比用户输入分母更大的结果，例如先后扣除不同分母的分数。此类余额照常精确保存、展示、继续扣库或退库；管理员提交未改动的规范余额时可以保留该值，不会因输入分母限制而被迫改库存。

## 免费材料

1. 总管理员先设置名称、型号、单位、每队数量、当前库存。
2. 队长核对材料、勾选确认并拍照领取；照片输入使用 `capture="environment"`，支持 jpg/png/webp，最多 5 MB。
3. 所有启用项目必须一次领齐，任一项目库存不足即整单失败。领取数量来自服务端设置，不能由队长伪造。
4. 一支队伍在现有系统中对应一个队长账号，以队长账号 ID 标识；相同显示队名不会自动合并账号。通过串行写事务和数据库部分唯一索引，保证每个队长最多一条有效领取记录。
5. 首队领取后锁定免费材料清单的名称、型号、单位、每队数量和启用状态，并禁止增删免费项目，保证其他队伍领取一致；仍可修改库存和排序。总管理员可更正个别记录，操作会审计。
6. 总管理员作废或删除有效领取记录会退回库存，并允许该队重新领取。重复作废不会重复退库。

统计包含已领取、未领取队伍、各材料发放合计、领取时间、IP 和照片。免费领取金额为 0；Excel 将材料、规格、数量、单位和零金额分列导出。

## 购买、核验与结算

1. 总管理员设置可购买材料的单价、当前库存，可额外设置每次限购。
2. 队长选择数量时前端实时计算金额；售罄项目禁选，数量上限受库存和限购约束。后端重新读取设置，以整数“分”计算单价、小计和总价，不信任请求中传来的金额。
3. 队长确认明细、拍照提交后生成待验证订单，发送验证码到其本人已验证邮箱。此时不扣库存，也不预留库存。新申请替代本人旧的待验证申请。
4. 验证成功时重新检查订单状态、邮箱、材料启用状态、单价和库存；价格改变时要求重新提交。通过 `BEGIN IMMEDIATE` 保留写锁，在 Python 中精确比较库存，并用带旧库存快照条件的 UPDATE 扣库；SQLite 不进行浮点数量运算。重复验证不能重复扣库。
5. 多项材料中任一项失败会回滚整笔扣库。扣库使用保存点回滚，并继续持有外层写锁直至订单取消，避免失败与其他确认请求交错。
6. 已确认订单初始为“未结算”，费用在比赛后统一记账。管理端显示每队购买合计及未结算应付合计；总管理员可逐笔或整队标记已结算，也可逐笔改回未结算。
7. 总管理员可更正数量、单价、备注，数量差额自动调整库存，总价重新计算；数量或单价更正后恢复未结算，需再次核对结算。作废/删除有效购买会退库，并从应付合计中排除。

记录保留材料和价格快照，修改目录价格不影响已确认记录。删除目录材料后历史快照仍在，但已断开的目录项目无法退回库存；该项目的待验证购买无法确认。建议有历史记录的售卖材料使用停用而非删除。

普通管理员只能查看、查看照片和导出；修改、删除、库存设置和结算接口均要求总管理员。材料业务变更与审计日志在同一数据库事务中提交；删除日志包含删除前的明细与金额。照片仅记录所属队长与管理员可查看；删除记录后清理对应照片。

Excel 包含“材料领取”“材料购买”“结算汇总”“库存”“领取统计”“发放汇总”六张表；购买表包含待验证、已取消等状态以便追溯，结算合计只计算已确认记录。沿用现有 Excel 文本防公式注入处理。

## 首次登录与共享验证码

队长和两类特批账号无论新旧，下次登录都必须填写姓名、大陆 11 位手机号并验证邮箱。导入的邮箱和旧预约邮箱不视为已验证。资料不完整时普通网页跳转 `/profile`，JSON 请求/API 返回拒绝使用的错误；允许资料验证、退出、切换语言、静态资源及健康检查。已有强制修改初始密码流程优先执行，再进入资料完善。资料完善期间不显示无法确认的强制公告或未签到弹窗。

后续更换邮箱必须重新验证；提交新邮箱后暂停使用系统，清除原邮箱的有效验证状态，取消未确认购买，验证完成后恢复使用。购买核验还会检查订单邮箱是否与当前已验证邮箱一致。手机号和姓名修改不要求重复验证原邮箱。

资料邮箱验证和购买验证共用 `app/verification.py`：

- 加密安全随机生成 6 位 ASCII 数字，有效期 5 分钟。
- 数据库仅存由应用 `SECRET_KEY` 计算的 HMAC-SHA256 摘要；绑定用途、记录 ID，资料验证码还绑定邮箱。
- 每个验证码最多 5 次错误，达到限制即失效；每条申请最多发送 5 次，重发冷却 60 秒，重发使旧码失效。
- 同一用户的资料及购买发送量共用数据库持久限制：每小时最多 10 次，跨进程检查；另有现有进程内限流。
- 邮件投递正文含验证码，数据库邮件日志和本地 outbox/失败归档正文均脱敏，不保存明文验证码。请求审计和安全事件也对 `code` 等字段脱敏。

真实邮件依赖现有邮件配置及 SMTP 环境，密码通过原有配置/环境提供，不写入源代码。未启用 SMTP 或使用保留测试域名时邮件只进入本地脱敏归档，无法从归档读取验证码；正式使用前须由管理员确认真实邮箱投递配置。pytest 和截图均使用测试验证码/隔离演示邮箱，没有发送真实邮件。

管理员改写通讯录邮箱不能替代本人验证。账号有材料记录时禁止直接删除，可先停用；个人信息清除功能同步清除已验证邮箱、验证时间和邮箱核验记录，并清除材料照片、IP 等个人字段。

## 服务器增量迁移与同步注意事项

迁移在应用启动时自动执行，入口在 `create_app()`，迁移保护在 `app/migrations.py`。**不要把开发环境的 `data/app.db`、密钥文件、邮件配置或运行目录覆盖到服务器。只同步源代码、模板和静态资源，继续使用服务器现有数据库及配置。**

迁移过程：

1. 对 SQLite 数据库旁的 `.migration.lock` 文件加操作系统锁，串行执行多 worker 的启动迁移。
2. 如果已有数据库缺少材料表、邮箱验证表或资料验证字段，先通过 SQLite online backup API 备份，兼容 WAL，文件权限为 `0600`；备份失败则停止启动。
3. 默认备份写到项目 `backups/app-before-materials-migration-<UTC时间>-<随机后缀>.db`；可通过应用 `BACKUP_DIR` 配置改变目录。
4. `db.create_all()` 只创建缺失表；原表通过 `ALTER TABLE ... ADD COLUMN` 逐项补齐，不重建、不删除已有表或记录。
5. `users` 新增可空字段：`verified_email VARCHAR(120)`、`email_verified_at DATETIME`、`profile_completed_at DATETIME`，旧账号不自动标记验证。
6. 创建六张业务表：`material_items`、`material_claims`、`material_claim_items`、`material_purchases`、`material_purchase_items`、`email_verifications`。
7. 创建部分唯一索引 `ux_material_claims_user_active`，约束 `status='active'` 时每个 `user_id` 只能有一条领取记录。只补充缺失的功能开关，保留已有开关值。
8. **已上线整数材料表也会自动升级**：为 `material_items` 增加 `stock_exact`、`per_team_qty_exact`、`max_per_purchase_exact` 三个可空 TEXT 字段；为 `material_claim_items` 和 `material_purchase_items` 各增加 `quantity_exact TEXT`。只用原整数列回填尚为空的新字段（如旧整数 3 → 精确字符串 `3`），保留原有整数列、所有记录 ID、照片、单价、总金额、验证码和结算状态；已有非空精确字段不会被覆盖。中途只完成部分字段的数据库可重新启动继续迁移。

新代码以 `*_exact` 为唯一数量依据，原整数列仅在新写入时保留数量整数部分的兼容镜像；历史迁移不会修改原列。不要再用旧脚本直接读写整数库存或执行 SQL `SUM(quantity)` 统计分数。数量统计使用精确有理数累加，金额统计继续使用整数分。**首次分数业务写入前必须停止所有旧版本 worker；旧版本无法理解分数库存，不能与新版本混跑。**

可重复启动：已有表、字段、索引和开关不会重复创建或覆盖。检测到缺少精确字段时也会先执行上述自动备份，再开始 ALTER/回填；完成后再次启动不会覆盖分数余额。若之前的未完成版本已经有多条有效领取记录，唯一索引会阻止启动；保留备份后人工核对记录和库存，禁止直接删库重建。

建议同步时先停止旧应用的所有 worker 和可能写库的脚本，再单独完成一次启动，确认成功后启动其余 worker，避免新旧代码同时运行。新代码自己的多 worker 启动有迁移锁保护。确保运行账户对 `data/` 和 `backups/` 有写权限及足够磁盘空间，并保留服务器原有 `SECRET_KEY`；更换密钥会使待验证代码失效，须重新发送。
