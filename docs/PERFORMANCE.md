# 页面加载性能：测量、瓶颈与优化（2026-11-13）

## 测量方法

`scripts/benchmark_pages.py` 在 `.runtime-tests/` 下建一个**临时数据库**（不连接 `data/app.db`，演示密码只在内存，不发真实邮件），按较真实的规模写入数据：100 名队长（每队 6 名队员）、3000 条预约（含同行人员）、800 条工具借用（40 张约 300 KB 的照片）、8000 条登录日志、6000 条操作日志、4000 条安全事件、300 条邮件记录。

- **服务端**：在本机回环地址启动 waitress（与生产相同的 WSGI 服务器），用 keep-alive HTTP 依次请求，每页预热 1 次后测 15 次，取中位数；同时统计每次请求执行的 SQL 条数和实际传输字节（客户端声明支持 gzip）。
- **浏览器**：Chromium（390 px 手机视口），用 CDP 模拟 150 ms 往返延迟、10 Mbit/s（接近经 Cloudflare 隧道访问的手机），同一页面连续访问 6 次，丢弃第 1 次（填充缓存），取其余 5 次到 `load` 事件的中位数。

复现：

```bash
.venv/bin/python scripts/benchmark_pages.py --out docs/perf_after.json --browser
.venv/bin/python scripts/benchmark_pages.py --compare docs/perf_before.json docs/perf_after.json
```

`docs/perf_before.json` 是在改代码之前、用同一脚本、同一数据量测得的。

## 找到的瓶颈

| 瓶颈 | 现象 | 处理 |
| --- | --- | --- |
| 列表页 N+1 查询 | 审核列表逐条懒加载队长/实验室/同行人员，并对每条待审核预约单独查一次冲突：待审核页 1893 条 SQL、全部页 4000 条；工具借用记录 1005 条；统计 752 条；申请记录 146 条 | `app/queries.py`：`selectinload` 预加载；待审核冲突改为一次查询后在内存按同一规则判断；锁定预约的值班联系人一次查出 |
| 静态资源每次都要重新验证 | `style.css` 为 `no-cache`，每次换页都多一次往返（经隧道约 150 ms）；样式表与基础脚本未压缩，脚本内联在每个页面里 | 按文件内容哈希生成 `?v=topnav-<hash>`，带版本号的 URL 返回 `public, max-age=31536000, immutable`；基础脚本移到可缓存的 `static/app.js`；CSS/JS/HTML gzip（CSS 23 KB→9.6 KB） |
| 工具照片 | 借用记录页把原图当 64 px 缩略图显示，且为 `no-store`，每次进入都重新下载全部照片（40 张约 12 MB） | `<img loading="lazy" decoding="async" width height>`；`/media/` 照片（随机文件名、不复用）改为 `private, max-age=86400`，仍逐次校验权限 |
| `/favicon.ico` 404 | 浏览器每次新开页面都会请求，且计入 404 统计 | 提供可缓存的 `static/favicon.svg` |
| 每个请求的固定开销 | 黑名单检查按 IP、设备分别查询 | 合并为一次查询（结果和顺序不变） |
| 缺少复合索引 | 冲突检测、队长记录、未读告警、黑名单等按多列过滤 | 增量迁移 `CREATE INDEX IF NOT EXISTS`（不改动、不删除任何数据）。试过日志表的 `(role, created_at)` 索引，会让 `LIMIT 300` 变成全量排序、反而更慢，已放弃 |
| 字体 | 只使用系统字体栈，没有网络字体下载 | 无需处理 |

说明：

- 小页面在服务端多了 0.3–1 ms（gzip 压缩和队长首页新增的概况查询），但传输字节减少 75%–85%，且每次换页少一次往返，经隧道访问时整体明显更快（浏览器测量约 315 ms → 165 ms）。
- 浏览器表中的「请求数」包含从内存缓存命中的 CSS/JS（不走网络），因此由 2 变为 3（多了单独的脚本文件），但耗时减少约一半。
- `/review/?status=all` 一次渲染全部约 3000 条记录（2.2 MB HTML），SQL 已从 4000 条降到 12 条，剩余时间主要在模板渲染和浏览器排版。继续优化需要分页，这会改变「全部」列表的现有行为，留给 Mark 决定。
